## Steps

1. Build a table-driven test that, for every new owner/organizer/admin route (list from the spec by `x-requirement`) and the key existing ones (`/owner/*`, `/club/{id}`, `/event/{id}`, `/promo/*`), calls it with: no token, USER token, another owner's token, and the right token, and asserts 401/403/404/200 as the spec says.
2. Include the P0.4 check: an owner or organizer cannot read another account's bookings, revenue or admin commission settings by changing an id.
3. Any gap found is fixed in the owning route (small) or recorded as a new item in `known-issues.md`.

## Update 2026-11-24 (client answers 02)

Phase 2. The suite now also covers the new access model (ADR-008), not only owner, organizer and admin:
- Club team roles (Owner, General Manager, Event Manager for assigned events only, Reservations Staff): one test per route family (events, bookings and check-in, revenue and refunds, payout destination, team changes) showing what each role may and may not do (T-104, T-105).
- Organizer permissions for quotes, chat and refunds: off by default, on only after the owner grants each one; a revoked grant stops access at once (T-106).
- Platform roles (Platform Admin, Platform Manager, Country Manager, Platform Staff): the sensitive actions (rates, payouts, payout destinations, Stripe settings, Technical Fee refunds, club debits, admin management) answer 403 for every role except Admin (T-107, T-108).
- Country scope: a Country Manager for Italy gets 404 for a French club or event on every admin route that lists or reads one.
- A pending partner gets 423 PARTNER_APPROVAL_PENDING and never 401 or 403.
- Refund authority follows T-139.
Done when (additions): the matrix test file has one row per role and route family and fails if a new route is added without a row; cross-club access returns 404 with the same body as an unknown id; the ten labelled test accounts (T-111) are used by the suite.
