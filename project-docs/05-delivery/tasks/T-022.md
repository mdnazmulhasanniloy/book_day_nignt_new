## Steps

1. Create the migration folder `backend/prisma/migrations/<ts>_add_pricing_rules/` and write the SQL by hand from `data-model.md` section 9, row 6. Update `schema.prisma` to match (`prisma migrate dev --create-only` is fine to scaffold; never `migrate reset`).
2. Create enums `ProductCategory`, `PricingRuleType`, `PricingScope`, `PricingValueType` and table `PricingRule` with its four CHECKs (`data-model.md` 8.2) and indexes. Add `Order.appliedFeeRuleId` and `appliedCommissionRuleId` (FK to `PricingRule`, RESTRICT).
3. Replace the two `Order` CHECKs as in 8.5: `serviceChargeAmount >= 0`, and `commissionAmount` conditional on `appliedCommissionRuleId`, plus `commissionAmount BETWEEN 0 AND grossAmount`. Add the new CHECKs as `NOT VALID`, then `VALIDATE CONSTRAINT` in the same migration. Drop the old CHECKs only after validation.
4. Replace `prevent_order_snapshot_mutation` so it also compares the two rule columns.
5. Seed GLOBAL rules (`effectiveFrom = '1970-01-01'`, `createdByAdminId = NULL`): FEE from `ServiceCharge(id='GLOBAL').amount` for TICKET, TABLE, CLUB_BOOKING (FIXED, perUnit false); COMMISSION from `ApplicationCharge` (EVENT percent for TICKET, TABLE, EXTRA; CLUB percent for CLUB_BOOKING). No FEE for EXTRA until Q2. Old orders keep NULL rule ids.
6. v1 write-through, SAME task and SAME release: `PATCH /admin/commission` and `PATCH /admin/service-charge` keep their request and response shapes and also write to `PricingRule` in the same transaction (end-date the current GLOBAL rule at `now()`, insert the new rule with `effectiveFrom = now()` and `createdByAdminId` = the acting admin). `ApplicationCharge` and `ServiceCharge` stay as the v1 mirror. Reads (`GET /admin/commission`, `/service-charge`, `/admin/service-charge`) are unchanged (BUG-B20 stays as is; v2 supersedes it).
7. Before the deploy, run the CHECK-violation queries from `reports/check-violations.sql` on a fresh restore: expected 0 rows.
8. Run the rehearsal script (T-002) from a clean restore. It must finish with exit code 0. Paste its summary (restore time, this migration's run time, backfill row counts, CHECK-violation counts) into the PR.
9. Update `data-model.md` (move this migration's text from section 8 to sections 2 to 6 only when the matching code ships) and `api-usage-map.md` if endpoints are affected.

## Client answer (2026-11-22)

Structure needs amendments before this migration is written (ADR-003): a VENUE scope, a fee display mode ("Service fee included"), a separate field for actual processing cost, and an optional partner-side fixed charge on free admissions. Confirmed: fee on every paid product (admin may set zero), commission borne by the club or organizer, overrides by client, venue, event and product, fixed amounts retained, versioned by effective date. Rule VALUES are not given (the 1.5% + EUR 0.26 figure is a test benchmark only).

## Amendment (client answers 2026-11-24)

Source: `01-discovery/client-answers-02.md`, ADR-003 (amended), ADR-012, ADR-005, ADR-008 as named below.

- Terminology: in the client's words the customer fee is the **Technical Fee** and the partner commission is the **Service Fee**. Table and column names are not renamed (the live app uses `serviceChargeAmount`).
- Structure changes to make before this migration is written (ADR-003 amendment): scopes COUNTRY, VENUE and TABLE_QUOTE added to `PricingScope`; `PricingRule` carries a percent part and a fixed part (`fixedValue`, `fixedCurrency`, `fixedOncePerOrder`); a field for the actual processor cost lives on the payment row, not on the rule (T-095). The extra columns are specified in `fee_fixed` (T-093); if T-093 is built first, fold the columns into this migration.
- Seed values (client answers Q1): FEE 5% plus EUR 0.50 once per order for IT, FR, MC, ES, US; COMMISSION 10% for TICKET, 15% for TABLE and EXTRA. The seeded GLOBAL rules must still reproduce today's totals until the gate (T-099) switches the fee model on.
- Size exception stays: this is one task with the v1 write-through.
