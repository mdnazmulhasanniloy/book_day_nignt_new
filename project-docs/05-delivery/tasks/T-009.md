## Steps

1. Accept optional `dateOfBirth` on `POST /auth/social`; validate with the existing `dob.utils.ts` rules; save it to the profile when sent.
2. Return `profileComplete` (boolean) in the response `data`: false while the date of birth is missing. Existing fields are untouched.
3. Retry safety: two concurrent or repeated calls with the same provider subject must create one account. Rely on the unique key from the oauth identity migration; catch the unique violation and return the existing user instead of 500.
4. Do NOT change signup role handling: `role: CLUB_OWNER` on signup (BUG-S03) stays open until the client answers D1.

## Result

Code commits on `feat/t-009-social-dob` (based on `ci/backend-tests`): b2618d7 (injectable verifier, no behaviour change), ed565af (feature), b8db66e (tests).

- `POST /auth/social` accepts optional `dateOfBirth` (ISO UTC, `assertSignupDob`), validated before the provider call and any write; invalid gives 422 and creates nothing. Saved only when the profile has no date of birth (never overwritten, also for existing users). Response `data` gains `profileComplete` (true when a DOB exists). No migration.
- Retry safety: user, profile and identity are created in one nested create (one transaction); a unique violation (P2002) on user or identity re-reads the existing account; the identity upsert tolerates a lost race; a phone collision retries once with the placeholder phone.
- Baseline (unmodified logic, 5 parallel identical calls): one account, no 500, because the existing email P2002 catch already handled it (Prisma logged 4 unique violations). So the concurrency test passed before and after; it guards the behaviour. The measurable gaps were the missing DOB/`profileComplete` and the non-atomic user + identity write.
- Tests: 10 DB-backed tests in `auth.social.db.test.ts` (all pass), run against a local throwaway database `t009_test`; rows created by the committing parallel tests are deleted in `after()`.
- Contract decisions to confirm: see open questions below.

Open questions for the product owner:
1. An under-age DOB sent at social sign-in is rejected with 422 and no account is created (same as signup). Should a social user who is under age be blocked entirely, or allowed without a DOB?
2. `profileComplete` means only "date of birth present". Other fields (gender, phone) are not part of it.
3. A DOB sent by an existing user who already has one is silently ignored (200, `profileComplete: true`), not an error.
4. A plain date (`2000-01-01`) is rejected like at signup; the client must send an ISO UTC datetime.

Not verified: real Google or Apple tokens, staging or production, Flutter (untouched).
