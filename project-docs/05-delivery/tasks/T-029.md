## Steps

1. Create the migration folder `backend/prisma/migrations/<ts>_backfill_geog/` and write the SQL by hand from `data-model.md` section 9, row 3. Update `schema.prisma` to match (`prisma migrate dev --create-only` is fine to scaffold; never `migrate reset`).
2. Write the data-only migration: `UPDATE "Event" SET geog = ST_SetSRID(ST_MakePoint(lng, lat), 4326)::geography WHERE geog IS NULL AND lat IS NOT NULL AND lng IS NOT NULL;` and the same for `Club`. Check the real column names in `schema.prisma` first (the SQL in the doc is a template).
3. Count affected rows before and after in the rehearsal backfill-counts query.
4. Run the rehearsal script (T-002) from a clean restore. It must finish with exit code 0. Paste its summary (restore time, this migration's run time, backfill row counts, CHECK-violation counts) into the PR.
5. Update `data-model.md` (move this migration's text from section 8 to sections 2 to 6 only when the matching code ships) and `api-usage-map.md` if endpoints are affected.

## Result

- Commits: `ec16e79` (DB test `geogBackfill.db.test.ts` and rehearsal SQL, failed before the migration with ENOENT on the migration file), `24d0317` (migration `20261123140000_backfill_geog`, rehearsal script section 7), docs commit follows.
- Migration: two idempotent UPDATEs (Club, Event) setting `geog` only where `geog IS NULL AND lat BETWEEN -90 AND 90 AND lng BETWEEN -180 AND 180`. No `schema.prisma` change (no drift). `lat`/`lng` are NOT NULL, so the only rows left NULL are those with NaN, Infinity or out-of-range values.
- Rehearsal on the restored dump: RESULT: PASS; this migration 0.010s; no drift beyond btree_gist. Dump counts: Club 9 rows, Event 11 rows; NULL geog with valid coordinates before 0 and after 0 for both; NULL geog with invalid coordinates 0 before and after. Because the dump had nothing to fill, the proof is on synthetic rows (in a rolled-back transaction in the rehearsal, and in the DB test): valid NULL rows filled, 4 invalid rows (lat 123, NaN, lng 200, Infinity) stay NULL, existing geog untouched, second run changes 0 rows.
- Tests: server `npm test` 96 pass 0 fail; `npm run test:db` 166 pass 0 fail (1 new); `tsc --noEmit` clean; worker untouched. `npm run lint` not run (intentionally skipped in this repo).
- Production-size risk: the UPDATE runs inside the migration transaction. For a table of a few thousand rows it is instant, but a very large table would hold row locks and write a large WAL in one transaction. Production has about 10 events and 10 clubs, so it is fine; if the tables grow to hundreds of thousands of rows, run the same statements as a batched separate script instead.
- Open questions: what to do with rows reported as invalid coordinates (none in the dump). New events and clubs written by unchanged code paths (notably duplicate) still get NULL geog until T-030.
