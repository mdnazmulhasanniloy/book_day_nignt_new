## Steps

1. Create `backend/prisma/migrations/<ts>_add_partner_approval/`; write the SQL by hand. Add enum `PartnerStatus` (PENDING, APPROVED, REJECTED) and table `PartnerApplication` (`userId` unique, `status`, `kind` OWNER or ORGANIZER, `decidedAt`, `decidedByAdminId`, `decisionNote`, timestamps). Update `schema.prisma`; never `migrate reset`.
2. Backfill in the same migration: one APPROVED row for every existing `CLUB_OWNER` user (Q23: existing clubs keep access, no reapproval). Users with role USER or ADMIN get no row.
3. Add a CHECK that a decided row has `decidedAt` and `decidedByAdminId`, and an index on `status`.
4. Run the rehearsal script from a clean restore and compare the number of APPROVED rows with `SELECT count(*) FROM "User" WHERE "accountRole" = 'CLUB_OWNER'`.
5. Update `data-model.md` migration 1 from deferred to active.

## Done when

- [ ] Rehearsal: the backfilled APPROVED count equals the CLUB_OWNER count on the dump (state both numbers in the PR).
- [ ] SQL test: a PENDING row without `decidedAt` is allowed, an APPROVED row without `decidedByAdminId` violates the CHECK.
- [ ] SQL test: two rows for the same `userId` violate the unique constraint.
- [ ] Rehearsal script (T-002) passes end to end on the restored dump, exit code 0; its summary is pasted into the PR.
- [ ] `npx prisma migrate diff` from the migrated rehearsal DB to `schema.prisma` shows no drift other than the known `btree_gist` item (BUG-B04).
- [ ] The previous release image still starts and passes `npm test` against the migrated DB (expand-only check).
- [ ] Docs updated in the same PR as the code (`api-spec.yaml`, `data-model.md`, `api-usage-map.md`, `known-issues.md` as they apply); `x-status: planned` removed only for what actually shipped.
- [ ] `npm run lint`, `npm run build` and `npm test` (in `backend/server/`, and `worker/` or `scheduler/` if touched) are green; DB-backed tests green with `npm run test:db`.
