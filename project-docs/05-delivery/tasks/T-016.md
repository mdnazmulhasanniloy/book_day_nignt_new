## Steps

1. Add `GET /ticket-tier-presets`: a static list (name, `tierType` TICKET or PASS, sort order) kept in code, public or any logged-in role as the spec says. Preset names come from the tracker A2.5 to A2.7; custom names stay allowed.
2. Accept `tierType` on tier objects in `POST /event` and `PUT /event/{id}` (Zod schema; default TICKET). Return it on tier responses (additive).
3. Section vs tier rule (formal): a section is a parent tier (no price, no capacity of its own), a tier is a child or a top-level priced tier. Validate: a section cannot have `soldCount`, a child's parent must be a section of the same event. Existing events are not re-validated on read.

- Choices: (a) `tierType` has no Zod default. Omitted on create = DB default TICKET; omitted on update = the stored value is kept, so the live app (which never sends it) cannot reset a PASS to TICKET. (b) The response keeps the spec shape (`ticketPresets`, `passPresets` string arrays, `sectionHelp`, `tierHelp`) and adds `presets[{name, tierType, sortOrder}]`; `sortOrder` is the position inside its own type, starting at 0. (c) The helper texts are my wording of the tracker A2.6 sentence. (d) The section rule is applied to the write path only: a tier that already has `soldCount > 0` and is sent with `children` returns 422 TIER_SECTION_HAS_SALES. Price and capacity stay required on parents (schema unchanged for old clients).
- Open questions: (1) Can a live event have a parent tier with its own sales and children? If yes, the 422 rule would block the live app from re-saving it. (2) The task asks for 422 on a child whose parent is in another event, but no request field can express that today; confirm whether a `parentId` field is wanted (not added, to avoid inventing API surface). (3) Final preset vocabulary ("can be aligned consistently across the app", A2.7).
