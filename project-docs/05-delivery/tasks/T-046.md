## Steps

1. Add optional `bucket=FUTURE|PENDING|PAST` to `GET /bookings`: FUTURE = confirmed and not yet ended; PENDING = guest-list pending or payment in progress; PAST = ended, canceled or refunded. `tab` keeps working unchanged.
2. Add `bookingStatus` to items: `CONFIRMED`, `GUEST_LIST_PENDING`, `PAYMENT_PROCESSING`, `CANCELED`, `REFUNDED`. Derive from Order and guest-list entry status; define the mapping table in the PR and in the spec.
3. Use the event's `timezone`/`endAt` for 'ended' (no local-time guesses).

## Result

- Commits: `22aae49` (failing tests), `6363413` (code), `6f24a47` (contract docs), docs commit (task, queue, release checkpoint). No migration, no schema change.
- `GET /bookings` gains optional `bucket=FUTURE|PENDING|PAST` (invalid value 422, wins over `tab`) and every item gains `bookingStatus`. Without `bucket` the old query, membership, order, paging and fields are unchanged (test on seeded data compares every key and value). With `bucket` the list is every order of the buyer (any status) plus the buyer's guest-list entries (by `EventGuestListEntry.userId`), classified in memory, newest first, paged. Guest-list items: `id` = entry id, `orderId` null, no `price`. The service throws on an empty user id.
- Mapping (first match wins; code in `bookings.bucket.ts`, same table in api-spec.yaml):

| Source | Condition | bookingStatus | bucket |
|---|---|---|---|
| Order | any Refund row (any Order.status, any Refund.status) | REFUNDED | PAST |
| Order PENDING_PAYMENT | club booking or module hold is EXPIRED | CANCELED | PAST |
| Order PENDING_PAYMENT | otherwise | PAYMENT_PROCESSING | PENDING |
| Order PAYMENT_FAILED | always | CANCELED | PAST |
| Order PAID | event eventStatus CANCELED | CANCELED | PAST |
| Order PAID | end <= now | CONFIRMED | PAST |
| Order PAID | end > now | CONFIRMED | FUTURE |
| Guest-list entry PENDING | always | GUEST_LIST_PENDING | PENDING |
| Guest-list entry REJECTED | always | CANCELED | PAST |
| Guest-list entry CONFIRMED | event CANCELED | CANCELED | PAST |
| Guest-list entry CONFIRMED | end <= now | CONFIRMED | PAST |
| Guest-list entry CONFIRMED | end > now | CONFIRMED | FUTURE |

- End = club booking `endAt`, `EventPurchase.eventEndAt`, or `Event.endAt` (module purchase, guest list), compared with the same fixed-CST wall clock as `tab` so FUTURE and UPCOMING agree. `Event.timezone` is not used (all existing events are UTC, nothing inferred).
