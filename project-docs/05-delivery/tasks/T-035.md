## Steps

1. Add `group=day` (buckets Today, Tomorrow, This Weekend, Upcoming) computed in the city's timezone when `cityId` is given, else the event's own `timezone`. Weekend = Friday 18:00 to Sunday end in that timezone (state the rule in the spec).
2. Add `from` and `to` (ISO dates, local to the same timezone rule) and `dateFilter=this_week` (Monday to Sunday).
3. Add `total` to the list meta (count of all matches ignoring paging, same filters).
4. Chronological default ordering by `startAt` (index `(eventStatus, startAt)` already exists).

- Time zone rule: city zone when `cityId` is sent, else the event own `timezone`. Existing events are all UTC, so they are grouped by UTC day (documented, not inferred from location). Buckets use the local date and weekday of the START (Intl in JS for the group, `AT TIME ZONE` in SQL for `from`, `to`, `this_week`), no fixed offsets.
- Rules stated in the spec: Today = local date of now (events that started earlier and still run count as Today), Tomorrow = next local date, This Weekend = Friday 18:00 to the end of Sunday of the current Monday to Sunday week, Upcoming = rest. `date` of a group = local date of its first item. Empty buckets omitted.
- Conservative choices: `group=day` is events only (clubs left out when type is omitted; type=CLUB gives 422); default order stays createdAt DESC unless group, from, to or this_week is used (then startAt ASC), so old clients see no change; the old `today`, `tomorrow`, `this_weekend`, `next_weekend` filters are untouched (server clock); the page is taken from the flat chronological list and then grouped. `meta.total` existed already and is the unpaged count.
- Open: a zone name PostgreSQL does not know (stored zones are validated with Intl) would make the date SQL fail; not seen in tests. The group `date` and empty-bucket choices are engineering choices to confirm with the Flutter side.
