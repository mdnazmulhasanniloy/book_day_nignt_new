  - `/recover/reset`: was validate, page token, existence, status, requireRecoverVerified; now page token, validate, existence, status, requireRecoverVerified.

- Choices: (1) validation sits directly after the token check (not after the existence and status checks) so a legitimate client with a valid token and a bad body keeps getting 422 as before. (2) `checkPassword` treats a missing password hash as a wrong password (401 INVALID_CREDENTIALS) so moving it before the status check cannot turn a blocked social-only account into a 500; this also turns the existing 500 for an active social-only account into 401 (not asked, needed for the reorder). (3) Unknown email is still answered before any bcrypt work, so response time can differ (not fixed).
- Open questions: none that block. Whether login should hide account status entirely even after a correct password is a client decision; the task says to keep the status message after a correct password and that is what was done.
