## Steps

1. Add a Redis-backed limiter middleware (fixed window, 20 requests per minute) keyed by IP and, when a valid token is present, by user id. Reuse the OTP limiter's helper if it is generic; otherwise add a tiny generic one in `src/app/middlewares/`.
2. Return 429 with `Retry-After` seconds and a stable `errorType` (`RATE_LIMITED`). Take the limit from a constant, not a literal in the route.
3. Make sure the IP comes from the trusted proxy header the app already uses (check `trust proxy` in `app.ts`); otherwise every request shares one key.

IP comes from `req.ip`; `app.ts` already has `trust proxy` 1.
- Choices: (1) the user id is read leniently from the bearer token (verifyAccessToken, no blacklist lookup) and a bad token is ignored, because `optionalUserAccessTokenMiddleware` would turn a stale token into a 401 and the live app logs out on 401. (2) A Redis failure is not failed open: the OTP limiter does not either (error goes to the global handler, 500). Open question: should checkout validation fail open when Redis is down? (3) Window and limit are the task and changelog suggestion (20 per minute), not a client-confirmed number. (4) Any rejected-by-validation or 404 attempt counts toward the limit, as does a valid one; a customer retyping codes legitimately stays far below 20 a minute.
