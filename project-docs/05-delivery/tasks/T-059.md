## Steps

1. Create the migration folder `backend/prisma/migrations/<ts>_add_analytics_indexes/` and write the SQL by hand from `data-model.md` section 9, row 13. Update `schema.prisma` to match (`prisma migrate dev --create-only` is fine to scaffold; never `migrate reset`).
2. Read the `Order` row count from the T-001 baseline and from production (read-only count, by the person with access). Rule: if `Order` is large (suggested threshold: more than 100,000 rows or any known long write lock window; confirm the number with the team and record it in the PR), create the indexes with `CREATE INDEX CONCURRENTLY`; otherwise a normal `CREATE INDEX` is acceptable.
3. Indexes: `Order(sellerUserId, status, createdAt)` and `Order(status, createdAt)`.
4. CONCURRENTLY cannot run inside a transaction block: put each `CREATE INDEX CONCURRENTLY` statement in its own migration folder with only that statement, and confirm in the rehearsal that `prisma migrate deploy` accepts it (if the db-migrator wraps it in a transaction and fails, apply those two statements by hand before the release and record that step in REL-M6).
5. Run the rehearsal script (T-002) from a clean restore. It must finish with exit code 0. Paste its summary (restore time, this migration's run time, backfill row counts, CHECK-violation counts) into the PR.
6. Update `data-model.md` (move this migration's text from section 8 to sections 2 to 6 only when the matching code ships) and `api-usage-map.md` if endpoints are affected.
