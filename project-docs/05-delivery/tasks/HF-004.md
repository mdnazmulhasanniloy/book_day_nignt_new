## Steps

1. Verify first, on staging or a local stack: call `POST /recover` (find user by email, returns the page token header/cookie per the spec), then call `POST /recover/reset` with that token and a new password WITHOUT calling `POST /recover/verify`. Record whether the password changed. The route chain for reset has `checkResetPasswordPageTokenMiddleware` and `checkUserExistenceMiddleware` but no OTP check.
2. If the reset does NOT work without OTP (something else enforces it): write the regression test that proves it, update `known-issues.md` S-19 to verified-not-exploitable, stop.
3. If it works (expected from code reading): on successful `POST /recover/verify`, write a short-lived Redis marker `recover:verified:<userId>` (TTL = page-token TTL). `POST /recover/reset` requires and deletes it; otherwise 403 with a stable `errorType` (not 401, see ADR-001 point 5). Use the existing `createRedisKey` helper and a new prefix in `const.ts`.
4. Contract stays the same for clients: same endpoints, same token, same success response. Check the Admin forgot-password flow (`admin/src/features/forgot-password`) and the Flutter recover flow call verify before reset (they do in the normal UI path).
5. Optional hardening in the same PR if trivial: reset may only be used once (the existing page-token blacklist already does this).
