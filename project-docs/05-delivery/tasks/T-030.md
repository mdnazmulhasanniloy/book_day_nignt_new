## Steps

1. Find every write path of `Event` and `Club` that sets lat/lng (create, update, duplicate, seed scripts) and make each set `geog` in the same statement or transaction.
2. `POST /event/{id}/duplicate` must copy or recompute `geog`.
3. Add a DB-level safeguard only if it is cheap (a trigger that sets `geog` from lat/lng on insert/update): if you add one it is a new migration with its own rehearsal run; otherwise keep it in code and add the check query to the rehearsal.

## Result

- Commits: `2332af7` (tests; failed before the code: event 4 of 8 failed, club 2 of 7 failed), `6bbf2e0` (code), docs commit follows.
- Code: new helper `backend/server/src/app/utils/geog.helpers.ts` (`syncGeogFromLatLng`) rebuilds `geog` from the lat/lng already stored on the row, inside the caller's transaction, and writes nothing when they are not finite or out of range. Used by event create, update and duplicate and club create and update. Update now recomputes when lat OR lng is sent (before: only when both, so a one-sided update left `geog` stale). An update that sends neither leaves `geog` alone. `scripts/seed-demo.ts` fills `geog` for its demo club and event (verified against a scratch DB: 0 rows with NULL geog and lat after two runs).
- Other write paths searched: `follow.services.ts`, `accountDeletion.utils.ts`, admin routes and the `vps-*` scripts do not write lat/lng. Hand-run SQL still bypasses the helper.
- Tests: `event.geog.db.test.ts` (7: create, update both, update one side, update without coordinates keeps geog, invalid 422 changes nothing, duplicate plus `/explore` ST_DWithin hit and a far centre miss, no NULL geog left), `club.geog.db.test.ts` (6), `geog.helpers.db.test.ts` (2: NaN, Infinity and out-of-range skipped for both tables). Server `npm test` 96 pass 0 fail; `npm run test:db` 181 pass 0 fail (15 new); `tsc --noEmit` clean. `npm run lint` and `npm run build` not run (lint intentionally skipped in this repo). No migration, so the rehearsal script was not run. Worker untouched.
- Conservative choices: no DB trigger (optional in the task, needs its own migration); invalid stored coordinates leave `geog` unchanged instead of failing the request (request bodies are already range-checked by Zod, so this only matters for legacy rows, e.g. duplicating one).
- Open question: whether to add a trigger later so hand-run SQL cannot leave `geog` stale. A NaN lat/lng stored by raw SQL makes Prisma reads of that row fail (500); not touched here.
- Not verified: staging, production, the previous release image against this code.
