## Result

- Commits: `ed358c5` (tests, failing first), `16e07eb` (code), docs commit follows.
- Code: `deleteEventModuleService` catches the Prisma error on `eventModule.delete` and maps it with `mapPrismaError` (T-012): P2003 becomes 409 FOREIGN_KEY_CONFLICT with the message 'Module has purchases and cannot be deleted; deactivate it instead' (module kept), P2025 becomes 404 'Module not found'. `createWishlistService` now throws `statusCode: 404` (was `status`) with errorType NOT_FOUND (additive) for a missing or unavailable club or event. Success paths unchanged.
- Tests: `eventModule/eventModule.delete.db.test.ts` (3) and `wishlist/wishlist.notFound.db.test.ts` (3), DB-backed hence the `.db.test.ts` names. On the unmodified code the delete-with-purchase test got 500 (expected 409) and the two wishlist 404 tests got 500. After: server `npm test` 35 pass; `npm run test:db` 104 pass 0 fail (98 + 6); worker tests 7 pass (run with TEST_DATABASE_URL set, worker untouched); `tsc --noEmit` clean in server. No migration so rehearsal not run. Lint and build not run (lint skipped in this repo). `api-spec.yaml` parses as valid YAML.
- Wrong-key grep (`status:` in thrown objects under `server/src`): `wishlist.services.ts` x2 (fixed here); `club.services.ts:35` `status: 422` in `POST /club` (not a CR-17 route; recorded as B-34, not fixed); `multer.middlewares.ts` has 12 `status: 400` keys inside `res.status(400).json({...})` bodies, which are sent directly, not thrown, so they are not affected.
- Clients (read only): Flutter `event_commerce_repository.dart:229` (module delete) and `wishlist_repository.dart:40` (add) map any 4xx other than 401/403 to a validation error with the server message and 5xx to a generic server error; nothing depends on the old 500. The admin app does not call either route.
- Not verified: behaviour on a deployed build or staging. `data-model.md` needs no change (no schema change).
- Conservative choices and open questions: the 409 keeps the generic errorType FOREIGN_KEY_CONFLICT from the T-012 mapper rather than a new module-specific code. A module with only expired or released purchases still cannot be deleted (the FK is Restrict); the docs and the client answers do not say whether such rows should be cleaned up or the module soft-deactivated, so no rule was invented.
