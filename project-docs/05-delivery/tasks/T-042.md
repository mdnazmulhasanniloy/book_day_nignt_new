## Steps

1. `GET /me/recently-viewed` from `UserRecentEventView`, newest first, paging.
2. `GET /explore/most-viewed?cityId&radiusKm`: sum of `EventViewDaily.views` over 30 days, city-scoped.
3. `sort=trending` on `/explore`: `views(7 days) + interested taps(7 days)` per Q6c. Fallback until 7 days of `EventViewDaily` exist: lifetime `Event.viewCount` (as the migration 11 note says).

- Routes: `GET /me/recently-viewed` (user bearer: checkUserAccessToken, checkUserExistence, checkAccountStatus; page and limit; own rows only; at most 20; newest first; skips deactivated events; items are explore event items plus `viewedAt`), `GET /explore/most-viewed` (public; `cityId` or `lat`/`lng`, `radiusKm` 10 to 50, `limit` 1 to 20 default 10, data only) and `sort=trending` on `GET /explore` (optional bearer as before). Registered before `/explore/:id`.
- Ranking (our proposal, open question): windows are whole UTC days ending with the UTC day of now (7 for trending, 30 for most viewed). Trending = views(7d) + Interested taps(7d), weight 1 each; most viewed = views(30d), zero-view events left out. Ties: startAt ASC, then id ASC. Fallback to lifetime `Event.viewCount` while no `EventViewDaily` row exists on or before the first window day. Code in `explore.ranking.ts`; the default order and every existing response are unchanged without `sort=trending`.
- Tests: server `npm test` 128 pass 0 fail (4 new pure tests); `npm run test:db` 309 pass 0 fail (11 new); server `tsc --noEmit` clean; worker and scheduler untouched. No migration, so the rehearsal script was skipped.
