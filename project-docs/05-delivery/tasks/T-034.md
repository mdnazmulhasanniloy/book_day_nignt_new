## Steps

1. Add optional `radiusKm` (10, 20, 30, 40, 50; default 20 so current clients are unchanged; other values return 422) and `cityId` (centre = city lat/lng) to `GET /explore`. `lat`/`lng` still work as the centre when given; `cityId` wins only when lat/lng are absent.
2. Return `distanceKm` (rounded to 1 decimal) on each item when a centre exists; field is additive.
3. Use `ST_DWithin` on the existing `geog` GiST index with the radius in metres; do not compute distance in JS for filtering.

## Result

- Commits: `69fa711` (tests; 7 of 11 failed first: radiusKm and cityId were ignored or unknown, 4 old-behaviour tests passed), `95c0fd4` (schema, service, types), docs commit follows. No schema change, no migration, so the rehearsal script was not run.
- Radius rule: allowed `radiusKm` 10, 20, 30, 40, 50 (else 422). The SERVER default when it is omitted stays 20, so the live app and old clients are unchanged. The client answer (Q6a, 2026-11-22) that the app INITIAL selection is 30 km is a client-app default: the new Flutter screens send `radiusKm=30` explicitly. 30 is NOT the server default.
- Centre: lat and lng when both are sent, otherwise the `City` lat/lng for `cityId` (any existing row regardless of `isLaunched`; all 11 seeded cities are inactive). Unknown `cityId` gives 404, a non-UUID gives 422. `radiusKm` with no centre has no effect (as before).
- Query: `ST_DWithin(geog, point, radiusKm * 1000)` for clubs and events (same GiST index as before); `distanceKm = ROUND(ST_Distance(geog, point) / 1000, 1)` computed in SQL, on every item only when a centre exists (additive). No JS distance filtering. Ordering and the rest of the response are untouched.
- Tests: `backend/server/src/app/modules/explore/explore.radius.db.test.ts` (11, DB-backed). Server `npm test` 103 pass 0 fail; `npm run test:db` 223 pass 0 fail (212 plus 11); `tsc --noEmit` clean in server; worker untouched. Lint, build and staging not run.
