## Steps

1. Write the failing tests first: create an event with 2 tiers, set `soldCount` to 3 on one, call `PUT /event/{id}` with the same tiers, assert `soldCount` and the tier `id` are unchanged (they are reset today).
2. Implement the ADR-004 rules in the update path: a tier object WITH `id` updates that row (the `id` must belong to this event, else 422); WITHOUT `id`, first try to match an existing tier of the event by `(groupName, tierName)` (the fallback for the live Flutter app, which does not send ids); only if there is no match, create a new tier. This task must NOT depend on migration 5: the matching query works without the new index (it is only slower).
3. A tier that exists but is missing from the array: delete it if `soldCount = 0`, otherwise keep it and mark `isActive = false` (see the diff doc for the exact rule). Never delete a tier that has any `EventPurchase` row for it once T-006 exists; for now `soldCount > 0` is the guard.
4. Changing `capacity` below the current `soldCount` returns 422 with a clear message. Changing the price of a tier with sales is allowed (old purchases keep their `pricePerPerson` snapshot).
5. Do the whole update in one transaction. Parents (sections) and children keep their `parentId` links by id after the update.
6. Update `api-spec.yaml` (`x-status`), `known-issues.md` (B-24) and `api-usage-map.md`.

- Matching rules implemented: id mode when any incoming tier has an id (foreign id 404, tiers without id created, duplicate id 422, a tier that owns children cannot become a child 422). Key mode otherwise: sections by trimmed case-insensitive (groupName, tierName), children by (matched parent id, tierName). Duplicate keys: exact (price, capacity) pairs first, then position by existing (sortOrder, createdAt, id) vs incoming array order; surplus incoming created; positional pairs with a different price or sales are logged as TIER_MATCH_AMBIGUOUS. Unmatched existing: deleted when soldCount = 0 and no surviving child, else isActive=false. Tier rows are locked with SELECT FOR UPDATE for the duration of the update.
- Conservative choices (open questions): omitted optional fields are written as null; a resent deactivated tier is reactivated because `isActive` defaults to true; a removed section with any sold child is deactivated, not deleted.
- Test file name deviation: the DB-backed tests are in \vent.tierUpdate.db.test.ts\ (not \vent.tierUpdate.test.ts\) so that pm run test:db\ picks them up and pm test\ skips them without a DB.
