## Steps

1. Treat `backend/bookdianight.dump` as personal data (S-06): restore it only to a LOCAL database, never to staging or production, and do not paste row contents into issues or PRs.
2. Start local PostgreSQL 16 with PostGIS (the compose file's `postgres` service, or a throwaway container on another port). Create an empty database `bookdia_rehearsal` with extensions `postgis` and `btree_gist`. Set `DATABASE_URL` for that database in a local, untracked env file.
3. Detect the dump format (`pg_restore --list` for custom format, else plain SQL via `psql`) and restore. Record restore time and any errors or warnings (ownership, extensions).
4. Run `npx prisma migrate status` against it. Record which migrations the dump already has applied (it should match the latest folder in `backend/prisma/migrations`, `20261111120000_oauth_identity`). If it is behind, run `prisma migrate deploy` (existing migrations only) and note which ran.
5. Write `05-delivery/reports/baseline-queries.sql` (SELECT only): row counts for `User`, `Club`, `Event`, `EventTicketTier`, `Order`, `EventPurchase`, `EventModulePurchase`, `Refund`; `Order` count by status; `EventTicketTier` soldCount totals; `Event` rows with `geog IS NULL`; duplicate `(eventId, groupName, tierName)` tier rows; `Order` rows violating the NEW CHECK rules of migration 6 (see T-002 for the list); `PromoCode` with neither or both of `eventId`/`clubId`.
6. Run it and save the output as `05-delivery/reports/baseline-YYYY-MM-DD.md` with counts only (no personal data). State the size of `Order`: T-059 uses it to decide on `CREATE INDEX CONCURRENTLY`.
