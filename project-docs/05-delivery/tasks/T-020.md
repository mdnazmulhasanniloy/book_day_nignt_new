## Steps

1. In the join service, look for an existing entry for the same user and event with status PENDING or APPROVED; if found return 409 `GUEST_LIST_DUPLICATE`. A REJECTED or canceled entry does not block a new request.
2. Make it race-safe: do the check and insert in one transaction, and prefer a partial unique index if the schema allows (otherwise a serializable transaction or `pg_advisory_xact_lock` on user+event). Any index is a migration: if one is needed, write it as an extra small migration with its own rehearsal run, or leave it out and document the race.
3. Access codes and the pending-hold rule are NOT part of this task (Q5).

No migration (rehearsal not run); worker and scheduler untouched.
- Built: in `joinGuestListService` the check and insert run in one `$transaction` after `pg_advisory_xact_lock(hashtextextended('guest-list-join:userId:eventId', 0))`; an existing PENDING or CONFIRMED entry for the same list and user throws 409 with errorType GUEST_LIST_DUPLICATE (not 401 or 403).
- Choices: (1) The schema status enum is PENDING, CONFIRMED, REJECTED: the docs word APPROVED means CONFIRMED. There is no cancelled status; only REJECTED is known to allow a new request (task text), taken as written. (2) No partial unique index: it would be a migration, userId is nullable, and production duplicates were not checked; the advisory lock is the task's stated alternative. The race is closed for the duplicate rule only; capacity checks before the transaction are unchanged and still racy (not in scope). (3) Entries with a null userId are not checked (the route requires a token, so new entries always have a user). (4) The 409 message is a new fixed string; the existing 409 messages are unchanged.
- Open questions: should a guest be able to re-join after the owner rejects (task says yes), and should the owner-side cancel/hold rules (24 hours, Q5) later change what counts as active? Access codes not part of this task.
